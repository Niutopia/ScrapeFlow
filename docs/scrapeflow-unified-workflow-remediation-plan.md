# ScrapeFlow 自动工作流规格与路线图

> 状态：当前产品基线
>
> 更新：2026-08-07
>
> 适用范围：单用户、本机运行、AList 媒体库

## 产品目标

ScrapeFlow 是一个自动管理 AList 影视库的本机服务。

把一个作品目录放进 `/quark/影视/待刮削/`，系统会自行识别作品、匹配 TMDB、判断电影或剧集、安排季集与目标目录，并完成整理、元数据写入、媒体库审计、缺口补源和清理。

用户的日常动作只有三件事：配置服务、放入来源、查看结果或处理最终错误。

```text
待刮削作品目录
  → 身份识别与规划
  → 写入正式媒体库
  → AList 刷新与精确回读
  → NFO / 海报 / 字幕处理
  → 正式库审计
  → 自动补齐可判定缺口
  → 清理任务拥有的临时内容
```

## 运行模型

```text
Web
  │ 提交来源、显示状态、暂停、重试、取消
  ▼
local.simple_server
  ├─ 入站监控与根任务调度
  ├─ 正式库审计与缺口分派
  ├─ provider 搜索和下载
  └─ 一个正式媒体库写入 worker
  ▼
Engine
  ├─ TMDB 匹配
  ├─ 电影、剧集、季集与命名规划
  └─ NFO、海报和文件计划
  ▼
AList
```

`local.simple_server` 是 Docker、Compose 和本地开发共用的 API 入口。Engine 负责业务判断；Local 负责任务状态、调度和实际 AList 操作。

## 自动流程

### 1. 来源整理

1. 系统从待刮削目录发现作品，或接收 `POST /api/jobs` 提交的目录路径。
2. Engine 自动取得身份、作品类型、年份、季集和正式库位置。
3. Local 将计划写入任务状态，并自动执行移动、改名、NFO、海报和字幕动作。
4. 每次远端写入后，系统刷新相关父目录并读取目标路径；路径、对象类型和字节数正确后才推进任务。
5. 成功后，系统清理该任务移动的来源和它创建的临时内容。

身份无法稳定判断时，系统继续使用文件名、目录上下文、年份、别名、媒体信息和已有库证据扩展匹配；策略耗尽后，将任务标记为 `failed_identity` 并保存原因。

### 2. 正式库审计与补源

审计会扫描电影、番剧和美剧目录，生成结构性任务与语义缺口。

- 缺正片、缺集和缺季：系统搜索候选、下载到任务专属 staging，再以内部子阶段走同一套识别和写入流程。
- 缺字幕：系统先检查同目录侧车和内嵌轨道；只有确认缺少配置语言时，才获取对应语言字幕并按已审计的视频路径写入同目录侧挂字幕。
- 补源 child 只写入缺失媒体，不新建每集 NFO 或海报；作品/季度级元数据遵循正式库现有结构。
- 缺 NFO 或海报：系统从已识别的作品资料直接补齐。

远端 staging 的边界固定为：

```text
/quark/影视/ScrapeFlow/补源/<root-job-id>/<attempt-id>
```

Provider 只能将文件写入这个目录。正式库位置、TMDB 身份、季集和文件名始终由 Engine 决定。

## 可靠性边界

- 正式媒体库的 move、rename、upload 和 delete 共用一把本机写锁。
- 写入后的事实来自 AList 的 fresh listing 和精确对象读取，而不是接口响应本身。
- 新对象短暂不可见时，系统会有界重试相关父目录的读取。
- 自动删除仅限任务从入站目录移动的内容、任务创建的 staging 和明确归类的临时项。
- 已存在的正式媒体不会因为名称猜测而删除。
- 重启后，执行中的任务先根据远端状态重新核对，再继续或进入可重试状态。

## 状态与目录

本机状态根由 `SCRAPEFLOW_STATE_DIR` 决定。活动服务使用：

```text
/data/
├── global-control.json
├── jobs/<job-id>.json
├── gaps/<job-id>/
├── library-audit/latest.json
└── locks/
```

这些目录保存任务和运行状态；它们不包含正式媒体。AList 数据库和正式媒体库需要单独维护，不能作为任务清理目标。

## 当前完成度

- 来源目录自动入队、身份识别、规划、写入、回读和清理已经覆盖活动测试。
- 正式库结构审计、可判定缺集/缺正片/缺字幕和元数据修复已进入自动流程。
- 视频补源、字幕侧挂、任务专属 staging、内部子阶段和失败重试均由自动运行时处理。
- Web 只展示根任务、审计和自动阶段；它不承担作品身份、候选或媒体路径决策。
- `npm run check` 覆盖静态检查、活动导入、Python 自动化测试和生产 Web 构建。

真实 AList、TMDB 和 provider 配置的联调仍需在上线窗口执行；该验证应包含一个新来源和一个已知缺口的完整闭环。

## 分阶段路线图

### 阶段 1：真实环境验收

在已配置的 AList、TMDB 和 provider 环境中分别运行一次来源整理和一次缺口补齐。记录任务阶段、最终路径、对象字节数、来源清理和 staging 清理结果。

### 阶段 2：故障演练

验证 AList 延迟可见、TMDB 暂时不可用、候选下载失败、服务重启和清理失败时的自动重试与最终错误展示。把真实环境发现的差异补成可重复的本地测试。

### 阶段 3：Engine 模块化

以当前自动化测试为保护，将 `engine/scrapeflow/core.py` 中相互独立的电影、剧集、文件命名和元数据规划逐步下沉到专用模块。每次拆分只改变内部组织，不改变任务输入、计划结果或 AList 行为。

### 阶段 4：运行状态维护

明确已完成任务、失败任务和审计快照的保留周期，并加入不影响正式媒体的状态清理。同步完善任务摘要和运维界面，让问题可以按来源、阶段和时间快速定位。

### 阶段 5：发布基线

每次发布前运行：

```sh
npm run check
docker compose --env-file .env.local build api gateway
```

随后在目标环境确认 `/api/health`、入站监控和一次端到端任务的结果。
